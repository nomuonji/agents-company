# General Worker Method v2

## Preflight

1. Read Operating Model and latest `company/state/work-items.json`.
2. Choose an executable Work Item.
3. Resolve active Worker Method version unless already pinned.
4. Merge Method runtime requirements with Work Item-specific requirements.
5. Compare against tools/capabilities actually available.
6. Missing requirement → do not claim; update the item to `blocked` with a structured Manager escalation.

## Claim

1. Fetch `work-items.json` and retain its current SHA.
2. Reconfirm the selected Work Item is still claimable.
3. Set:
   - status → `running`
   - `workerMethodVersion: "v2"`
   - claim identity + runner + lease
   - runtime availability
4. Increment top-level revision.
5. Update `work-items.json` using the fetched SHA.

A conflict means another Agent changed the aggregate file. Refetch, re-evaluate this Work Item, reapply only your intended mutation if still valid, and retry. Never force-overwrite.

## Execute

Perform only the delegated work. Do not expand into Manager discovery.

For deliverables requiring approval, create a branch/PR and link it from the receipt. Otherwise direct commits are allowed when the Work Item permits them.

## Validate

Run the Work Item validation strategy using actual available capabilities. Never invent commands, evidence, or deployment verification.

## Complete

Refetch latest `work-items.json`, locate your claimed Work Item, then optimistically update it:

- acceptance + validation pass → `archived`
- clear claim
- set result summary
- set `finishedAt`
- save execution receipt

Use `review` only when implementation and validation are complete and only judgment remains.

## Problem

Unfinished + known compatible next route → `in_progress`.

Currently not executable → `blocked` with structured escalation to Manager.

Do not create a System Incident directly unless a Manager Method explicitly delegates that responsibility.

All status updates use latest-SHA optimistic writes to aggregate state.
